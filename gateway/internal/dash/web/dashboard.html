Nothing unauthenticated enters the ledger

Every transfer carries a signed token and an idempotency key. A retry returns the original saga instead of creating a second one; rejects and fraud holds never reach the engine at all.

Deterministic replay, not hopeful recovery

The engine persists every transition to a write-ahead log and tracks its position in the event stream. Restart after a hard kill and the same sagas come back, byte for byte, proven by a scripted drill.

Measured, never asserted

Latency and match rates are committed run logs with the hardware they came from. The RUSTGO performance bar is unclaimed until a run supports it, and the page says which is which.

Settlement decisions, itemized

The engine matches every operator row back to the transfer that created it: exact amount, small fee tolerance, and every exception it cannot explain. Each figure below comes from the live report.

How a transfer settles

Four steps, each with a runnable check behind it.

01

Authenticate

JWT plus idempotency key, rate limited per client, body and amount bounded.

02

Apply rules

Velocity, new-account amount limits and cross-operator impossible hops hold traffic for review.

03

Log the saga

The engine appends each transition to the write-ahead log before it is observable.

04

Match settlement

Operator rows join to sagas by transaction id; exceptions queue with reasons.

Partition and recovery

Holding traffic pauses the engine's intake exactly like a network partition, and releasing it replays the backlog. The kill-9 drill is scripted so it fails loudly.

Stop the engine process (kill -9), start it again with the same environment, then compare the settlement report before and after. scripts/recovery.ps1 runs it and fails if one byte differs.

Run it before you read about it

Five minutes on one machine: seed ten thousand transfers, load them through the gateway, upload the settlement file, and watch the report match the expected counts exactly.
